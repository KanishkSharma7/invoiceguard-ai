# InvoiceGuard AI — formal testing and security checklist

Prepared from implementation inspection and updated after automated execution on September 26, 2026. **282 automated tests passed**, plus the running-API smoke test and four live Gemini cases. Two backend defects were fixed. No final manual browser/visual/assistive-technology pass was performed. See [automated results](AUTOMATED_TEST_RESULTS.md).

Status applies to the whole checklist row: automated-only cases fully exercised are Passed; repaired cases are Failed → Fixed → Passed. A mixed `both` case stays Not Tested until its manual/UI portion is exercised, with its successful automated subcheck recorded in the execution column. Partially exercised automated rows also remain Not Tested; this does not mean their listed assertions failed. The original coverage column is retained as the 69-test baseline, and the execution column supplies current evidence.

## Scope and how to use

Inspected React routes/forms/detail components, API client and CSS; Express authentication/middleware/routes/errors; deterministic checks, Gemini adapter and persistence service; shared Zod contracts; Prisma models and both SQL migrations; seed/configuration/workspace manifests; all three test files, smoke/live scripts, and project documentation. Generated dependencies/build artifacts and local secrets are not application source and are not reproduced here.

- API paths below are relative to `/api/v1`, except `/api/health/*`. UI runs at `http://localhost:5173` with same-origin API proxy.
- Plan fixtures: organization A with OWNER/REVIEWER/VIEWER, distinct organization B, same/different vendor IDs, a normal invoice and three earlier same-currency histories. Seed supplies OWNER/REVIEWER and three vendors; VIEWER/org B/malformed database rows require isolated test fixtures. Do not damage existing demo records to create negative cases.
- Default price fixture: Printer paper cartons at USD25 across three distinct older invoice numbers. Preserve valid arithmetic when testing price changes. Payment terms are elapsed issue-to-due days; there is no free-text terms field.
- `manual` requires browser, assistive-technology, configuration or source inspection. `automated` describes a repeatable unit/API/database scenario, including automation still to be written. `both` requires automated logic/API verification **and** manual UI/live behavior verification. Test type does not claim an existing test.
- Coverage: **Direct** means the cited assertion directly covers the core behavior at the stated layer; **Partial** covers only listed variants/layers; **None** means no matching assertion in the 69-test suite. A direct unit/API mapping never certifies UI behavior. Every `manual` and `both` row requires fresh manual verification; uncovered automated variants also remain pending.
- Mock Gemini for deterministic failure/adversarial cases. Live calls are separately authorized test execution and consume quota; never require an exact model sentence/recommendation except when controlling mocked output. AI safety invariants must hold regardless of the recommendation.
- Current implementation permits human corrections between all three valid decision states with fresh concurrency tokens. It rejects PENDING/unknown decision values; it does **not** implement a restrictive approval-state machine. No invoice-edit UI, vendor-management/history page, file upload, password recovery, payment execution, general audit UI, durable worker, or production deployment is in scope.
- Expected results are acceptance criteria grounded in source, not observations. Explicit inspection risks/limitations are noted where behavior may fall short; record failures later rather than silently treating current code as proof.
